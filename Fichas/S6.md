## 1. Enquadramento e Objetivos de Aprendizagem

Na Engenharia de Software profissional, o software não é considerado construído (ou desenvolvido) até ser verificado e testado de forma automatizada. A escrita de código executável sem uma suite de testes que garanta a sua correção contínua gera uma dívida técnica insustentável. Esta sessão introduz a disciplina rigorosa da Garantia de Qualidade (QA), distinguindo a verificação formal do código em relação à especificação, a estruturação da Pirâmide de Testes e a prática metodológica do *Test-Driven Development* (TDD) sob o lema *"Scaffold First, Automate Second"*.

### Objetivos Específicos:
- **Distinguir defeito, erro e falha:** compreender a cadeia de causalidade no software e aplicar o conceito de Oráculo de Teste (*test oracle*) para verificação objetiva.
- **Dominar a pirâmide de testes:** estruturar uma suite equilibrada com forte base de Testes Unitários (rápidos e isolados), testes de integração intermédios e testes E2E/Sistema no topo.
- **Aplicar técnicas de caixa-negra e caixa-branca:** derivar casos de teste de limites recorrendo a Partições de Equivalência (PE) e Análise de Valores Limite (AVL), bem como medir a Cobertura de Código (*Line/Branch Coverage*).
- **Praticar o ciclo TDD (Red-Green-Refactor):** escrever primeiro o teste que falha (*red*), implementar o código mínimo funcional para passar (*green*) e refatorar para Clean Code mantendo os testes a verde.
- **Isolar dependências com Test Doubles (mocks/stubs):** utilizar objetos simulados (*mocks*) para isolar a lógica de negócio de dependências externas lentas ou instáveis (ex.: bases de dados e APIs de IA/RAG).

### Exercício 2.1: Taxonomia de Falhas e Análise de Valores Limite (Caixa-Negra)

#### Enunciado:
Considere a especificação do módulo do Museu Soares dos Reis referente ao cálculo da tarifa de bilheteira e atribuição de descontos de incentivo a jovens e famílias:
- Visitantes com idade $< 12$ anos: Entrada Gratuita (Tarifa $0,00\ \text{€}$).
- Jovens entre $12$ e $25$ anos (inclusive): Desconto Jovem de 50% (Tarifa $4,00\ \text{€}$).
- Adultos entre $26$ e $64$ anos (inclusive): Tarifa Inteira ($8,00\ \text{€}$).
- Seniores com idade $\ge 65$ anos: Desconto Sénior de 25% (Tarifa $6,00\ \text{€}$).
- Idades inválidas ($< 0$ ou $> 120$ anos): Lançar exceção `IllegalArgumentException` / `ValueError`.

Identifique as Partições de Equivalência (PE), defina os Valores Limite (VL) a testar, estabeleça o Oráculo de Teste e indique o Tipo de Teste.

#### Resolução Técnica:

| Partição de Equivalência (PE) | Valores Limite (VL) a Testar | Resultado Esperado (Oráculo) | Tipo de Teste |
| :--- | :--- | :--- | :--- |
| **PE1: Idade Inválida Negativa** | $\text{idade} = -1$, $\text{idade} = -100$ | Lança `ValueError` / `IllegalArgumentException` | Caixa-negra (Exceção) |
| **PE2: Infantil ($< 12$ anos)** | $\text{idade} = 0$, $\text{idade} = 11$ | Tarifa $= 0.00\ \text{€}$ (Gratuito) | Caixa-negra (Fronteira) |
| **PE3: Jovem ($12$ a $25$ anos)** | $\text{idade} = 12$, $\text{idade} = 25$ | Tarifa $= 4.00\ \text{€}$ (50% Desconto) | Caixa-negra (Fronteira) |
| **PE4: Adulto ($26$ a $64$ anos)** | $\text{idade} = 26$, $\text{idade} = 64$ | Tarifa $= 8.00\ \text{€}$ (Inteira) | Caixa-negra (Fronteira) |
| **PE5: Sénior ($\ge 65$ anos)** | $\text{idade} = 65$, $\text{idade} = 120$ | Tarifa $= 6.00\ \text{€}$ (25% Desconto) | Caixa-negra (Fronteira) |
| **PE6: Idade Inválida Superior** | $\text{idade} = 121$ | Lança `ValueError` / `IllegalArgumentException` | Caixa-negra (Exceção) |

### Exercício 2.2: Ciclo de Desenvolvimento Dirigido por Testes (TDD)

#### Enunciado:
Analise a sequência rigorosa de passos do ciclo TDD para a implementação do componente `ValidadorRecompensa` (responsável por atribuir medalhas digitais e vouchers de desconto na loja do museu ao completar desafios de QR Code). Descreva a ação das equipas de engenharia e o estado esperado da suite de testes para cada uma das três fases.

#### Resolução Técnica:

| Fase TDD | Ação das Equipas de Engenharia | Estado da Suite de Testes & Métrica |
| :--- | :--- | :--- |
| **RED** *(escrever teste)* | Escrever um teste unitário automatizado em PyTest/JUnit que especifica um novo comportamento funcional (ex.: verificar se a leitura de 3 QR Codes atribui o Voucher *"Desconto 10%"*). O código de produção ainda não existe. | **FALHA ESPERADA** (`AssertionError` ou erro de compilação/importação). Comprova a sensibilidade do teste e afasta a ocorrência de falsos positivos. |
| **GREEN** *(código mínimo)* | Escrever o código de produção estritamente mínimo e mais simples possível para fazer o teste passar. Não procurar abstrações ou perfeição arquitetural nesta fase. | **PASSA A VERDE**. A totalidade dos testes executa com sucesso. O comportamento funcional foi validado pelo oráculo. |
| **REFACTOR** *(clean code)* | Melhorar a qualidade interna do código (eliminar duplicações, melhorar nomenclatura, extrair constantes) sem alterar o comportamento externo. | **PROTEÇÃO CONTÍNUA**. A suite de testes garante que nenhuma regressão funcional foi introduzida pela refatorização. |

### Exercício 2.3: Isolamento de Dependências com Mocks (`Mockito` / `unittest.mock`)

#### Enunciado:
O serviço `ServicoAssistenteIA` da app do museu precisa de consultar um motor de IA/RAG externo para responder a dúvidas sobre obras como *O Desterro*. No entanto, efetuar chamadas reais à API durante a execução dos testes unitários causaria lentidão, custos de latência e falhas por falta de rede nas paredes espessas de pedra do museu.  
Explique por que razão a utilização de um Mock (Objeto Simulado) é indispensável para testar a lógica de tratamento de respostas do serviço sem invocar o servidor remoto de IA.

#### Resolução Técnica:
1. **Preservação da Natureza do Teste Unitário:** Um teste unitário puro tem de ser executado em memória, de forma determinística, rápida ($< 10\ \text{ms}$) e sem dependências de infraestrutura externa. Chamar a API remota violaria este isolamento, transformando o teste num teste de integração.
2. **Eliminação de Não-Determinismo e Latência:** A rede e os tempos de inferência de modelos de linguagem introduzem atrasos consideráveis e falhas intermitentes (*flaky tests*) que quebram pipelines de CI/CD.
3. **Controlo de Custos e Quotas:** Cada invocação de uma API de IA externa tem custos financeiros associados e limites de taxa de chamadas (*rate limits*). O Mock permite simular milhares de invocações a custo zero.
4. **Verificação de Contratos e Exceções Raras:** Com o Mock é possível simular cenários de limite difíceis de forçar em produção (ex.: *HTTP 504 Gateway Timeout*, payloads JSON corrompidos ou alucinações de formato) e inspecionar se a camada de negócio tratou a resposta adequadamente (`assert_called_once_with(...)`).

## 3. Imersão no Caso de Estudo: Suite de Testes do Museu Soares dos Reis

A suite de testes deve atingir uma cobertura $\ge 80\%$ (medida via Coverage.py ou JaCoCo), respeitando a Pirâmide de Testes:

| Nível da Pirâmide | Componentes Alvo no MNSR | Estratégia & Ferramenta |
| :--- | :--- | :--- |
| **Base (70%)**<br>Testes Unitários | `CalculadorAfluencia`, `ValidadorQRCode`, `GeradorRoteiroTempo`, `ValidadorRecompensa`. | PyTest / JUnit 5. Execução ultrarrápida ($< 1\text{s}$), sem acesso a BD ou rede. |
| **Meio (20%)**<br>Testes de Integração | `ServicoAssistenteIA` + `MockClienteRAG`, `RepositorioObra` + BD em memória (SQLite `:memory:` / H2). | `unittest.mock` / Mockito. Valida a comunicação inter-camadas com dependências simuladas. |
| **Topo (10%)**<br>Testes de Sistema / E2E | Fluxo completo da Caça ao Tesouro desde a leitura simulada de QR Code até à emissão de voucher. | `TestClient` / REST Assured. Valida endpoints HTTP e códigos de estado (200 OK, 400 Bad Request). |

### Passo 4.2: Prática de TDD na Função `CalculadorAfluencia`

#### 1. RED (Teste que falha):
```python
# tests/test_calculador_afluencia.py
import pytest
from src.business.calculador_afluencia import CalculadorAfluencia

def test_deve_retornar_afluencia_elevada_quando_visitantes_superam_500():
    calc = CalculadorAfluencia()
    resultado = calc.determinar_nivel(visitantes_atuais=501)
    assert resultado == "ELEVADA"
```

#### 2. GREEN (Implementação mínima funcional):
```python
# src/business/calculador_afluencia.py
class CalculadorAfluencia:
    def determinar_nivel(self, visitantes_atuais: int) -> str:
        if visitantes_atuais > 500:
            return "ELEVADA"
        return "NORMAL"
```

#### 3. REFACTOR (Clean Code sem números mágicos):
```python
# src/business/calculador_afluencia.py
class CalculadorAfluencia:
    CAPACIDADE_MAXIMA_SALAS = 500
    CAPACIDADE_MEDIA_SALAS = 250

    def determinar_nivel(self, visitantes_atuais: int) -> str:
        if visitantes_atuais > self.CAPACIDADE_MAXIMA_SALAS:
            return "ELEVADA"
        elif visitantes_atuais >= self.CAPACIDADE_MEDIA_SALAS:
            return "MEDIA"
        return "BAIXA"
```

### Passo 4.3: Implementação de Testes com Mocks para o `ServicoAssistenteIA`
```python
# tests/test_servico_assistente_ia.py
from unittest.mock import Mock

class ServicoAssistenteIA:
    def __init__(self, cliente_rag):
        self.cliente_rag = cliente_rag

    def responder_pergunta(self, obra: str) -> str:
        conteudo = self.cliente_rag.consultar(obra)
        return f"Guia MNSR: {conteudo}"

def test_servico_assistente_ia_com_mock():
    cliente_rag_mock = Mock()
    cliente_rag_mock.consultar.return_value = "Escultura em mármore de António Soares dos Reis (1872)."

    servico = ServicoAssistenteIA(cliente_rag=cliente_rag_mock)
    resposta = servico.responder_pergunta("O Desterro")

    assert resposta == "Guia MNSR: Escultura em mármore de António Soares dos Reis (1872)."
    cliente_rag_mock.consultar.assert_called_once_with("O Desterro")
```
